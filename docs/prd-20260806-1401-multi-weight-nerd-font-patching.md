### 1.2 Product summary

The Multi-Weight Variants pipeline has reached a shape-preserving ceiling: 427 native glyphs (374 contour/topology mismatches + 53 not equalizable by the available exact operations) remain incompatible between masters and are slated for type-designer review. This PRD is a deliberate scope change to the approved Multi-Weight Variants initiative. It introduces a **Native Glyph Fallback** policy so the interpolation pipeline can produce the new weights deterministically today, and it adds a second product flavor — the **Nerd Font Flavor** — generated by running the pinned Nerd Fonts Patcher v3.5.0 after the base fonts are built.

The fallback copies the Regular outline into the affected Medium/SemiBold (and stretch) glyphs so the output remains renderable and deterministic; it is a known visual limitation that must be disclosed, not a repair of the 427 glyphs. The Nerd Fonts Patcher is **additive**: it inserts icon glyphs at Private Use Area codepoints and never replaces native Latin, Greek, Cyrillic, digit, or punctuation glyphs. The only overwrite surface is the verified 15 PUA codepoints shared with Fantasque stylistic alternates and native Powerline symbols — and only in the Nerd Font Flavor. The Base Flavor is never touched.

The Nerd Font Flavor is produced **always-on** inside the existing build pipeline (a dedicated Docker stage, no new workflow inputs) for every released monospace weight, with full artifact and format parity (TTF, OTF, WOFF, WOFF2, independent manifests, checksums, archives, family names, and release notes). The product goal is parity with the Nerd Fonts ecosystem: developers who standardize on Nerd Fonts icon workflows can adopt Fantasque Sans Mono — in every weight the multi-weight initiative ships — without patching fonts manually.

## 2. Goals

### 2.1 Business goals

- **Parity with the Nerd Fonts ecosystem**: Make Fantasque Sans Mono available as an official Nerd Font flavor with the complete v3.5.0 icon set, so developers who standardize on Nerd Fonts icon workflows (Powerline, Devicons, Font Awesome, Material Design Icons, and friends) can adopt the font without a second thought.
- **Remove the community patching burden**: Today users patch Fantasque Sans Mono themselves or rely on third-party patched forks; an official flavor removes fragmentation, support load, and inconsistent quality across unofficial builds.
- **Complete the Multi-Weight Variants offering**: Every weight the multi-weight initiative ships (core weights, and stretch weights that pass their release gates) is also available with icons in one bundle, strengthening the competitive position of the font among programming fonts.

### 2.2 User goals

- **Developer & terminal user**: Install one Nerd Font Flavor that brings the complete icon set across every released weight, so terminal, tmux, and IDE setups render icons correctly without manual patching.
- **Fork Owner**: Receive both the Base Flavor and the Nerd Font Flavor from every Custom Build automatically, without learning a new configuration option.
- **Type Designer**: Keep a verifiable quality gate — collision reports and visual review of the small overwrite surface — so the flavor never damages Fantasque's native glyphs silently.

### 2.3 Non-goals (Out of Scope)

- **Repairing the 427 incompatible native glyphs**: The fallback copies Regular outlines into affected new weights; the manual harmonization backlog stays open and is handled by type designers separately. The patcher is not a repair mechanism.
- **Modifying the Base Flavor**: The patcher never mutates Base Flavor artifacts, `.sfdir` sources, or existing webfont outputs. In multi-weight builds the fallback (FR-2) intentionally changes the outlines of the 427 affected glyphs in the new weights only — that change is disclosed, not silent; builds with multi-weight disabled keep today's artifact set and behavior unchanged (FR-7.1).
- **New CI surface**: No new workflow, job, or Actions step. Patching runs inside the existing `docker build` step via a dedicated Docker stage; `test-multi-weight.yml` (a pytest-only smoke gate) is unaffected.
- **Proportional (non-monospace) Nerd Font variant**: Only monospace weights are covered by this proposal.
- **Patcher version drift**: Only the pinned, checksum-verified Nerd Fonts Patcher v3.5.0; never the moving `master` branch and no unpinned upgrades.
- **Curating or redesigning bundled icon sets**: Icon glyphs are bundled as-is from the upstream v3.5.0 release with their licenses.
- **Variable Font (VF)**: Remains a V2 target (see parent PRD GH-006).
- **Changing the protected legacy toolchain**: `CON-001` stands — no modification to legacy sources or `Scripts/features.py`; all work goes through the Docker build stages and existing packaging scripts.

## 4. Functional requirements

### FR-1: Two Product Flavors (Priority: CRITICAL)

The product ships two independent flavors. The **Base Flavor** is the existing Fantasque Sans Mono output, and the **Nerd Font Flavor** is the same fonts augmented with the complete Nerd Fonts icon set.

- **FR-1.1**: In single-weight mode (`enable_multi_weight = false`), the Base Flavor MUST remain exactly as it is today — same artifacts, naming, manifest structure, and rollback path (regression gate FR-7.1, SM-T4). In multi-weight mode, the Nerd Font patcher MUST NOT mutate, replace, or rename Base Flavor outputs or their protected `.sfdir` sources (`CON-001`); the only Base Flavor changes in that mode are the disclosed native-glyph fallbacks of FR-2, which belong to the multi-weight pipeline itself and are not patcher effects.
- **FR-1.2**: The Nerd Font Flavor MUST be produced as a separate output namespace: distinct family names, file names, archives, manifests, and checksums (see FR-5). It MUST never write over Base Flavor TTF, OTF, WOFF, WOFF2, or `.sfdir` files.
- **FR-1.3**: Flavor activation is **always-on within the multi-weight pipeline**: every build with multi-weight enabled MUST produce both flavors, with no new `workflow_dispatch` input and no user-facing configuration. Builds with multi-weight disabled MUST NOT produce Nerd Font artifacts and MUST retain today's exact behavior (FR-7).

### FR-2: Native Glyph Fallback (Priority: CRITICAL)

The 427 native glyphs that remain incompatible between masters (374 contour/topology mismatches + 53 not equalizable) are not repaired by this feature; they are handled by a documented fallback so interpolation produces deterministic, renderable output.

- **FR-2.1**: The glyph status boundary MUST distinguish three outcomes: `compatible` (normal interpolation), `fallback_regular` (Regular outline substituted), and `needs_harmonization` (still tracked in `tracking.json` for manual type-designer work). The 427 glyphs currently tracked as incompatible are classified `fallback_regular` by this policy.
- **FR-2.2**: The fallback MUST be applied only to a temporary interpolation input derived from the harmonized masters — protected masters are never modified. For each fallback glyph used by the Regular↔Bold interpolation, the Bold-side outline MUST be made identical to the Regular outline so the output glyph resolves to the Regular outline by construction, deterministically.
- **FR-2.3**: Validation output MUST record the fallback count, glyph names, source master, and reason per weight, and MUST distinguish structural interpolation passes from fallback glyphs. This report is part of the release evidence.
- **FR-2.4**: The fallback MUST be disclosed to users as a known visual limitation: release notes and README MUST state that some glyphs in Medium/SemiBold (and stretch weights, if released) render with the Regular outline. The Visual Quality Rubric MUST classify the weight inconsistency as an accepted limitation for release (decision recorded 2026-08-06) — not as a silent pass.

### FR-3: Nerd Font Icon Augmentation (Priority: CRITICAL)

The Nerd Fonts Patcher adds icon glyphs to the font. It is additive by contract — it never replaces native glyphs.

- **FR-3.1**: The patcher MUST be invoked in a mode that merges the complete icon set into the font without removing, altering, or replacing native Latin, Greek, Cyrillic, digit, and punctuation glyphs. Only codepoint collisions (FR-4) may result in overwrites, and only in the Nerd Font Flavor.
- **FR-3.2**: The patcher MUST be pinned to the official Nerd Fonts Patcher release `v3.5.0` with a verified checksum. Tracking the moving `master` branch is forbidden (reproducibility contract).
- **FR-3.3**: The patcher MUST be invoked with the `--complete` policy so the full available icon set of v3.5.0 is included.
- **FR-3.4**: The patcher MUST be applied to every released monospace weight: Regular, Bold, Italic, BoldItalic, Medium, SemiBold, and any stretch weight that passes its release gate. A weight missing from the Nerd Font Flavor while present in the Base Flavor is a release blocker (parity, FR-5).

### FR-4: Collision Policy & Collision Report (Priority: HIGH)

The verified collision surface is exactly **15 PUA codepoints**: U+E000–E007 (Fantasque stylistic alternates), U+E0A0–E0A2 and U+E0B0–E0B3 (native Powerline symbols). No native letter is ever touched.

- **FR-4.1**: In the Nerd Font Flavor only, the patcher MAY overwrite existing glyphs at the verified collision list. Any overwrite outside this list MUST fail the build gate.
- **FR-4.2**: The Base Flavor MUST never be overwritten by any collision policy, in any build mode.
- **FR-4.3**: A collision report MUST be generated per weight, comparing the patched flavor against its pre-patch input and listing every codepoint whose glyph changed. The report MUST confirm zero drift from the 15-codepoint baseline; any drift MUST block the release (gate).
- **FR-4.4**: The overwritten surface MUST undergo visual review by a Type Designer before release, so valid Fantasque glyphs are not changed unknowingly.

### FR-5: Artifact & Format Parity (Priority: HIGH)

A patched TTF without regenerated webfont outputs is incomplete; both flavors must be fully packaged.

- **FR-5.1**: Both flavors MUST ship TTF, OTF, WOFF, and WOFF2 for every released weight, plus their manifests.
- **FR-5.2**: The Nerd Font Flavor MUST have independent manifests, checksums, archive names, family names, and release notes. No file or checksum from the Base Flavor MAY be reused for the Nerd Font Flavor.
- **FR-5.3**: Naming follows the Nerd Fonts ecosystem convention: family name "Fantasque Sans Mono Nerd Font"; files named `FantasqueSansMonoNerdFont-{Weight}.{ext}` (e.g., `FantasqueSansMonoNerdFont-Medium.ttf`). Base Flavor names remain `FantasqueSansMono-{Weight}.{ext}`. The two naming sets MUST NOT collide.
- **FR-5.4**: All Nerd Font OTF and webfont outputs MUST be generated from the patcher outputs (patched TTF as the source of truth); shipping a webfont derived from an unpatched base font in the Nerd Font Flavor is a defect.

### FR-6: Licensing & Attribution (Priority: HIGH)

Nerd Fonts v3.5.0 aggregates multiple icon sets (Pomicons, Powerline Symbols, Seti-UI, Devicons, Font Awesome, Material Design Icons, and others). The flavor must carry the required upstream licenses.

- **FR-6.1**: The Nerd Font Flavor package MUST include the upstream license texts and an attribution manifest covering 100% of the bundled icon sets enabled by `--complete`. The manifest MUST list each icon set, its license, and its source.
- **FR-6.2**: The Base Flavor package MUST remain unchanged and carry only its existing contents (OFL-1.1 for Fantasque outlines). No license regression in either flavor.

### FR-7: Backward Compatibility (Priority: CRITICAL)

- **FR-7.1**: Builds with `enable_multi_weight = false` MUST retain the current base output behavior — the same artifact set, naming, and pipeline behavior as today, with no Nerd Font Flavor and no patcher execution. This is a hard regression gate (behavioral/non-mutation, SM-T4). Note: byte-identity is NOT a requirement — build manifests embed a dynamic `build_timestamp` by design (`Scripts/configure.py`), and the build driver only mitigates FontForge output non-determinism via `SOURCE_DATE_EPOCH` (`Scripts/custom_build_driver.py`).
- **FR-7.2**: Enabling the Nerd Font Flavor MUST NOT mutate, replace, or invalidate Base Flavor artifacts produced in the same build.
- **FR-7.3**: The `test-multi-weight.yml` workflow (pytest-only smoke gate) MUST remain unaffected. No new workflow, job, or Actions step is introduced by this feature (FR-8).

### FR-8: Pipeline Placement (Priority: HIGH)

The patcher runs as a dedicated Docker build stage inside the existing `docker build` step of `custom-build.yml` — the repository's only artifact-producing workflow.

- **FR-8.1**: A dedicated Docker stage (`builder-nerd-patcher`) MUST run between Stage 1 (`builder-fontforge`) and Stage 2 (`final`), deriving from Stage 1 so it inherits the FontForge runtime without adding FontForge to the final packaging image.
- **FR-8.2**: The patched outputs MUST be copied into Stage 2 via `COPY --from=builder-nerd-patcher` before `Scripts/packaging.sh` runs, and MUST be consumed by the existing hinting, conversion, and packaging steps.
- **FR-8.3**: The workflow file (`custom-build.yml`) MUST keep its current step structure — no new workflow, job, or Actions step. `test-multi-weight.yml` is untouched.
- **FR-8.4**: Total build duration (Base Flavor + Nerd Font Flavor, all weights) MUST complete within **≤ 300 minutes** on a GitHub Actions free-tier runner (the parent PRD caps the multi-weight pipeline at ≤ 240 minutes; patching and regenerated webfonts carry the headroom). Exceeding the cap is a release blocker.

### FR-9: Post-Patch Validation Gates (Priority: MEDIUM)

- **FR-9.1**: Before publication, the Nerd Font Flavor MUST pass post-patch gates: vertical metrics unchanged from the base weight, monospace advance widths preserved, family naming correct per FR-5.3, and output completeness (every released weight in every format).
- **FR-9.2**: The patcher MUST write exclusively into its own output namespace inside the build stage; it MUST NOT write to base font directories, `.sfdir` sources, or existing webfont output paths.
- **FR-9.3**: A validation gate MUST compare the patched flavor with its pre-patch inputs and record codepoint collisions, changes to native glyphs, vertical metrics, advance widths, family naming, and output completeness — this record accompanies the release (see FR-4.3).

## 5. User experience

### 5.1 Entry points & first-time user flow

- **Release page**: Each release presents two clearly labelled groups of archives — the Base Flavor (`FantasqueSansMono-*`) and the Nerd Font Flavor (`FantasqueSansMonoNerdFont-*`). Release notes explain the difference in one line and link to the icon-usage section of the README.
- **README**: A "Nerd Font Flavor" section describes installation, icon usage in terminals/IDEs, the collision policy, and the native-glyph fallback limitation (FR-2.4).
- **Custom Build**: No new entry point — the Nerd Font Flavor is included automatically whenever multi-weight is enabled (FR-1.3).

### 5.2 Core experience

- **Install**: The user downloads the Nerd Font Flavor archive for their platform format (TTF or OTF), installs it through the standard OS mechanism (Windows right-click → Install, macOS Font Book, Linux `~/.local/share/fonts/`), and selects **"Fantasque Sans Mono Nerd Font"** in their terminal, tmux, or IDE.
- **Icons render**: Powerline, Devicons, Font Awesome, Material Design Icons, and the rest of the v3.5.0 icon set render at their standard codepoints — no patching, no configuration.
- **Weights work as expected**: Medium, SemiBold, and stretch weights carry the same icon set as Regular and Bold; the 427 fallback glyphs render with the Regular outline, which is disclosed and visible in the specimen.

### 5.3 UI/UX highlights & Edge cases

- **Side-by-side install is safe**: Distinct family names ("Fantasque Sans Mono" vs "Fantasque Sans Mono Nerd Font") mean both flavors can be installed at once without name collision or confusion.
- **Apps without PUA support**: Applications that cannot render Private Use Area codepoints show blank/tofu boxes for icons — standard Nerd Fonts behavior, disclosed in the README; it never affects native text.
- **Fallback disclosure**: The weight inconsistency of the 427 fallback glyphs is surfaced in release notes and the README rather than hidden; the Visual Quality Rubric classifies it as an accepted limitation.
- **Stretch weights**: Light/ExtraBold appear in the Nerd Font Flavor only if they pass their release gates; until then the flavor covers the core weights only, and release notes say so explicitly.

## 8. Technical considerations (Input for Engineering Team)

### 8.1 Integration points

- **Dockerfile**: A new dedicated stage `builder-nerd-patcher` derives from Stage 1 (`FROM builder-fontforge`) so it inherits the verified FontForge runtime; Stage 2 (`final`) gains a `COPY --from=builder-nerd-patcher` for the patcher outputs before `Scripts/packaging.sh` runs. Stage 2 itself stays free of FontForge.
- **`Scripts/packaging.sh`**: Gains a flavor branch — Nerd Font packaging, independent manifest/checksums, archive naming per FR-5. Base packaging behavior is unchanged.
- **`.github/workflows/custom-build.yml`**: Unchanged step structure (FR-8.3). Activation flows through the existing multi-weight pipeline inputs; no new `workflow_dispatch` input (FR-1.3).
- **Validation scripts**: `validate_harmonization.py` / `validate_interpolation.py` gain the `fallback_regular` outcome and report fields (FR-2.1, FR-2.3); the interpolation driver gains the fallback preparation path (FR-2.2).
- **Post-patch gates**: New validation comparing patched vs pre-patch inputs (metrics, widths, naming, completeness) and the collision report (FR-4.3, FR-9).
- **Specimen & docs**: Specimen generator and README updated for the Nerd Font Flavor, fallback disclosure, and icon usage (FR-2.4, §5).
- **Architecture docs**: `docs/ARCHITECTURE.md` is known to drift from the current harmonization/multi-weight state; it MUST be refreshed (via `sdlc-map-architecture`) before the Specification phase. The patcher placement decision may warrant a new ADR (candidate: ADR-0004) during the Spec phase — the placement was verified against the current `Dockerfile` in the discovery draft (Rev 3).

### 8.2 Data storage & privacy

- No user data is collected, stored, or transmitted by this feature; all artifacts are built and published through the existing GitHub Actions + GitHub Releases flow.
- Release packages embed third-party license texts and the attribution manifest (FR-6); checksums and manifests are generated per flavor for auditability.
- The collision audit relies on codepoint data from the pinned v3.5.0 distribution; the pinned distribution and its checksum are part of the build inputs, not runtime data.

### 8.3 Scalability & potential technical challenges

- **Patching runtime**: Up to 7 weights × 2 formats (TTF/OTF) patched per build; patching and regenerated webfonts must fit within the ≤ 300-minute build budget (FR-8.4). Parallelizing patching runs is the obvious lever.
- **Reproducibility**: The patcher source and icon data MUST be pinned to v3.5.0 and checksum-verified (FR-3.2); any nondeterminism in the patcher (timestamps, ordering) must be assessed during the Spec phase against the repository's deterministic-build contract.
- **Format & metadata divergence**: Patching changes metrics, widths, and naming; OTF and webfont outputs must be regenerated from the patcher outputs with independent checksums — stale base-derived files are a defect (FR-5.4).
- **Future icon-set drift**: Newer icon sets may collide with Fantasque's PUA ranges beyond the verified 15 codepoints; the collision report is the gate that catches drift (FR-4.3), so it must run per weight per build.
- **Release size**: The Nerd Font Flavor roughly doubles archive surface; release-size growth should be tracked but is accepted as inherent to the feature (the icon set is the point).
- **Visual review burden**: The 427-glyph fallback and the 15-codepoint collision surface require Type Designer time; the collision surface is small by design, the fallback backlog is tracked separately in `tracking.json`.
